Test layers · Reporting

UI and API test reports: same skeleton, different evidence

The template should differ — but not into two unrelated documents. Keep one reporting standard; change what each layer records as environment, coverage, evidence and metrics.

2 layers 3 coverage matrices 2 defect templates

What stays identical

The outer structure is the decision artifact, and it must look the same in a UI report, an API report and a combined release report:

  • Verdict format: Go / No-Go / Go with conditions.
  • Status taxonomy: passed, failed, blocked, not run, flaky.
  • Severity scale, priority scale and defect ID scheme.
  • Section order: metadata → summary → scope → results → defects → risks → recommendation.
  • The rule that every failure carries evidence, an owner and a next step.

This follows the standard test-summary-report structure (IEEE 829 / ISO 29119 lineage). Only the content inside the sections changes by layer.

Where the two diverge

DimensionUI test reportAPI test report
Unit under test User journey, screen, component state. Endpoint or operation, contract.
Environment block Browser and version, OS, device, viewport, zoom, locale, network throttling. Service name and version or image tag, gateway URL, auth scheme and scopes, tenant, DB seed, downstream services or mocks, OpenAPI spec version.
Evidence Annotated screenshot, recording, console errors, HAR. Request/response pair (redacted), status and body, correlation or trace ID, service logs, schema diff.
Coverage Journeys × browsers/devices; visual states (empty, loading, error); accessibility; i18n. Operations × methods × status codes; authz matrix; validation and boundaries; contract; idempotency.
Key metrics Cross-browser pass rate, flake rate (first run vs retry), visual diffs, a11y violations, Core Web Vitals. p50/p95/p99 latency vs budget, error rate by status class, schema-validation failures, spec coverage %.
Usual tools Playwright, Cypress, axe-core, Percy or Chromatic, Lighthouse. Postman/Newman, REST Assured, Karate, Pact, Schemathesis, k6 or Gatling.
What “blocked” usually means Staging UI down, third-party widget or CAPTCHA, broken test account. Service or dependency down, token issuer broken, DB seed mismatch, mock drift.
Severity drivers User-blocking flow, data loss on screen, keyboard trap, broken layout. Data corruption, authz bypass, contract break, core 5xx, latency SLA breach.

Also declare, or mark out of scope

  • Visual states: empty, loading, error, partial data, long strings.
  • Accessibility: WCAG 2.2 AA, keyboard-only operation, a screen reader, contrast, 200% zoom.
  • i18n, RTL and responsive breakpoints.
  • Visual regression baselines: which diffs are intentional and which are defects.
  • Flake reporting: first-run results separately from retries, because retries mask real bugs.

What an API report adds

An API report replaces the browser matrix with service state and a contract. Its evidence is the request and response, not the screen.

Service and contract block (example)

EndpointMethodHappyValidationAuthZSchemaResult
/ordersPOSTPass4/5 passPassPassFail — BUG-401

The auth matrix is the API equivalent of cross-browser testing: anonymous / customer / support / admin × every operation → verify 401, 403 or 200.

Also include

  • Contract verification: response schema validated against OpenAPI; breaking changes flagged.
  • Idempotency and retries: the same key applied twice, and what the second call returns.
  • Data integrity: database state before and after, side effects verified.
  • Rate limiting and concurrency: 429 behaviour, race conditions.
  • Performance, if in scope: p95/p99 against a per-operation budget.
  • Error taxonomy: is a 500 truly 5xx? Do validation errors return 422 or 400 consistently?
Hard rule

Never include tokens, cookies or PII in request/response evidence. Redact headers and bodies in the report; attach full logs to the ticket only if policy allows.

Defect entries differ too

Same fields, different evidence. The UI entry proves what a user saw; the API entry proves what the service returned.

Attribute cross-layer failures correctly

A UI test failing does not automatically make it a UI defect. Classify by where the fix belongs.

  • UI test fails because the API returns 500. The symptom is UI; the root cause is API. Count the defect once, under API, list affected journeys as impact, and have the UI report link to the API defect instead of opening a duplicate.
  • The API fails but the UI handles it gracefully. One API defect; correct error-state behaviour may be a product requirement, not a bug.
  • The API fails and the UI white-screens, hangs or loses input. A second, separate UI defect: missing error handling.

Add two fields to every defect — layer detected and root-cause layer — and aggregate them in the summary:

Root-cause layerOpen defectsBlocking
UI31
API22
Shared / infrastructure10

One release report, both layers

Produce one release report with layer sections rather than two top-level reports. Leaders want one verdict; QA needs the separate detail.

Release report outline 
1. Release verdict (single, conditions listed)
2. Scope and test layers: UI suites, API suites, what each excluded
3. Results — UI: journey × browser matrix, a11y, visual
4. Results — API: operation × status-code matrix, auth matrix, contract
5. Performance (per layer, if in scope)
6. Defects: one list, tagged by detected layer and root-cause layer
7. Risks, accepted gaps, residual risk by layer
8. Evidence index: /evidence/ui, /evidence/api

Exit criteria differ by layer

UI exit criteria

  • All P0 journeys pass on the agreed browser and device matrix.
  • Zero open severity-1 UI defects.
  • Zero critical accessibility violations.
  • Visual diffs reviewed and intentional.
  • Flake rate under the agreed threshold.

API exit criteria

  • 100% of in-scope operations covered with happy path, main negative cases and authz.
  • 100% schema validation.
  • No open P1.
  • p95 within budget.
  • Contract diff reviewed and backward compatible across supported versions.
  • No secrets found in logs.

The practical rule

Build one reporting standard with layer-specific modules: shared summary, verdict and defect taxonomy; an environment block, coverage matrices, evidence format and metrics that instantiate differently for UI and API. In an automated pipeline this is a layer: ui | api label plus different artifacts per layer, feeding the same report generator.

The template differs in content, not in standard. One skeleton, two evidence languages — and a single verdict a release manager can act on.

Báo cáo kiểm thử UI và API: cùng khung, khác bằng chứng

Biểu mẫu nên khác nhau — nhưng không phải thành hai tài liệu rời rạc. Giữ một chuẩn báo cáo duy nhất; thay đổi những gì mỗi tầng ghi lại: môi trường, độ phủ, bằng chứng và chỉ số.

2 tầng 3 ma trận độ phủ 2 biểu mẫu lỗi

Những gì giữ nguyên

Cấu trúc ngoài là công cụ ra quyết định, và nó phải giống nhau trong báo cáo UI, báo cáo API và báo cáo phát hành tổng hợp:

  • Định dạng kết luận: Go / No-Go / Go có điều kiện.
  • Hệ thống trạng thái: đạt, không đạt, bị chặn, chưa chạy, chập chờn.
  • Thang mức độ, thang ưu tiên và quy ước ID lỗi.
  • Thứ tự các phần: siêu dữ liệu → tóm tắt → phạm vi → kết quả → lỗi → rủi ro → khuyến nghị.
  • Quy tắc mỗi lỗi phải có bằng chứng, người phụ trách và bước tiếp theo.

Điều này theo cấu trúc báo cáo tổng kết kiểm thử chuẩn (dòng IEEE 829 / ISO 29119). Chỉ nội dung bên trong các phần thay đổi theo tầng.

Hai báo cáo khác nhau ở đâu

Khía cạnhBáo cáo UIBáo cáo API
Đơn vị kiểm thử Hành trình người dùng, màn hình, trạng thái thành phần. Endpoint hoặc thao tác, hợp đồng (contract).
Khối môi trường Trình duyệt và phiên bản, OS, thiết bị, viewport, zoom, locale, điều kiện mạng. Tên dịch vụ và phiên bản hoặc image tag, URL gateway, cơ chế auth và scope, tenant, seed DB, dịch vụ phụ thuộc hoặc mock, phiên bản spec OpenAPI.
Bằng chứng Ảnh chụp có chú thích, video, lỗi console, HAR. Cặp request/response (đã che dữ liệu), status và body, correlation hoặc trace ID, log dịch vụ, diff schema.
Độ phủ Hành trình × trình duyệt/thiết bị; trạng thái hình ảnh (rỗng, đang tải, lỗi); khả năng tiếp cận; i18n. Thao tác × phương thức × mã trạng thái; ma trận authz; kiểm tra hợp lệ và biên; contract; idempotency.
Chỉ số chính Tỷ lệ đạt đa trình duyệt, tỷ lệ chập chờn (lần đầu so với retry), visual diff, vi phạm a11y, Core Web Vitals. Độ trễ p50/p95/p99 so với ngân sách, tỷ lệ lỗi theo lớp mã trạng thái, lỗi xác thực schema, % bao phủ spec.
Công cụ thường dùng Playwright, Cypress, axe-core, Percy hoặc Chromatic, Lighthouse. Postman/Newman, REST Assured, Karate, Pact, Schemathesis, k6 hoặc Gatling.
“Bị chặn” thường nghĩa là UI staging sập, widget bên thứ ba hoặc CAPTCHA, tài khoản test hỏng. Dịch vụ hoặc phụ thuộc sập, nơi cấp token hỏng, seed DB lệch, mock lệch.
Yếu tố quyết định mức độ Luồng chặn người dùng, mất dữ liệu trên màn hình, bẫy bàn phím, vỡ bố cục. Hỏng dữ liệu, vượt quyền authz, phá vỡ contract, 5xx lõi, vi phạm SLA độ trễ.

Báo cáo UI cần thêm gì

Ngoài khung dùng chung, báo cáo UI mang bằng chứng cho thấy môi trường là một phần của kết quả.

Cũng phải khai báo, hoặc đánh dấu ngoài phạm vi

  • Trạng thái hình ảnh: rỗng, đang tải, lỗi, dữ liệu một phần, chuỗi dài.
  • Khả năng tiếp cận: WCAG 2.2 AA, thao tác chỉ bằng bàn phím, trình đọc màn hình, độ tương phản, zoom 200%.
  • i18n, RTL và các điểm ngắt responsive.
  • Baseline visual regression: diff nào là chủ đích, diff nào là lỗi.
  • Báo cáo chập chờn: tách kết quả lần chạy đầu khỏi retry, vì retry che giấu lỗi thật.

Báo cáo API cần thêm gì

Báo cáo API thay ma trận trình duyệt bằng trạng thái dịch vụ và hợp đồng. Bằng chứng là request và response, không phải màn hình.

Ma trận auth là tương đương API của kiểm thử đa trình duyệt: anonymous / customer / support / admin × mọi thao tác → xác minh 401, 403 hoặc 200.

Cũng cần có

  • Xác thực hợp đồng: response schema được kiểm tra với OpenAPI; thay đổi phá vỡ được gắn cờ.
  • Idempotency và retry: cùng một khóa áp dụng hai lần, lần gọi thứ hai trả về gì.
  • Toàn vẹn dữ liệu: trạng thái DB trước và sau, side effect được xác minh.
  • Rate limit và concurrency: hành vi 429, race condition.
  • Hiệu năng, nếu trong phạm vi: p95/p99 so với ngân sách từng thao tác.
  • Phân loại lỗi: 500 có đúng là 5xx? Lỗi validation trả 422 hay 400 có nhất quán?
Quy tắc cứng

Không bao giờ đưa token, cookie hay PII vào bằng chứng request/response. Che header và body trong báo cáo; chỉ đính kèm log đầy đủ vào ticket nếu chính sách cho phép.

Mục lỗi cũng khác nhau

Cùng bộ trường, khác bằng chứng. Mục UI chứng minh người dùng thấy gì; mục API chứng minh dịch vụ trả về gì.

Quy lỗi về đúng tầng

Một test UI thất bại không tự động là lỗi UI. Phân loại theo nơi bản sửa thuộc về.

  • UI test fail vì API trả 500. Triệu chứng ở UI; nguyên nhân gốc ở API. Đếm lỗi một lần dưới API, liệt kê các hành trình bị ảnh hưởng là tác động, và để báo cáo UI liên kết tới lỗi API thay vì mở lỗi trùng.
  • API lỗi nhưng UI xử lý gọn gàng. Một lỗi API; hành vi trạng thái lỗi đúng có thể là yêu cầu sản phẩm, không phải bug.
  • API lỗi và UI trắng trang, treo hoặc mất dữ liệu đã nhập. Đó là lỗi UI thứ hai, riêng biệt: thiếu xử lý lỗi.

Thêm hai trường vào mọi lỗi — tầng phát hiện và tầng nguyên nhân gốc — và tổng hợp chúng trong phần tóm tắt:

Một báo cáo phát hành, hai tầng

Tạo một báo cáo phát hành với các phần theo tầng thay vì hai báo cáo cấp cao riêng biệt. Lãnh đạo muốn một kết luận; QA cần chi tiết riêng.

Dàn ý báo cáo phát hành 
1. Kết luận phát hành (một, kèm điều kiện)
2. Phạm vi và tầng kiểm thử: bộ UI, bộ API, phần loại trừ của mỗi tầng
3. Kết quả — UI: ma trận hành trình × trình duyệt, a11y, visual
4. Kết quả — API: ma trận thao tác × mã trạng thái, ma trận auth, contract
5. Hiệu năng (theo tầng, nếu trong phạm vi)
6. Lỗi: một danh sách, gắn nhãn tầng phát hiện và tầng nguyên nhân gốc
7. Rủi ro, khoảng trống được chấp nhận, rủi ro tồn dư theo tầng
8. Mục lục bằng chứng: /evidence/ui, /evidence/api

Tiêu chí kết thúc khác nhau theo tầng

Tiêu chí kết thúc UI

  • Tất cả hành trình P0 đạt trên ma trận trình duyệt và thiết bị đã thống nhất.
  • Không còn lỗi UI mức 1.
  • Không có vi phạm khả năng tiếp cận nghiêm trọng.
  • Visual diff được review và có chủ đích.
  • Tỷ lệ chập chờn dưới ngưỡng đã thống nhất.

Tiêu chí kết thúc API

  • 100% thao tác trong phạm vi có happy path, các ca negative chính và authz.
  • 100% xác thực schema.
  • Không còn P1.
  • p95 trong ngân sách.
  • Diff contract được review và tương thích ngược với các phiên bản hỗ trợ.
  • Không có bí mật trong log.

Quy tắc thực dụng

Xây một chuẩn báo cáo duy nhất với các module theo tầng: phần tóm tắt, kết luận và phân loại lỗi dùng chung; khối môi trường, ma trận độ phủ, định dạng bằng chứng và chỉ số khởi tạo khác nhau cho UI và API. Trong pipeline tự động, đó là nhãn layer: ui | api cộng với artifact khác nhau theo tầng, cùng đổ về một bộ sinh báo cáo.

Biểu mẫu khác nhau ở nội dung, không khác ở chuẩn. Một khung, hai ngôn ngữ bằng chứng — và một kết luận duy nhất để release manager hành động.
