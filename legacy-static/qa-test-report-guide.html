How to write a QA test report

A test report exists so someone else can decide — ship, fix first, or stop — with the least possible reading. Web UI testing adds one rule: the environment is part of the result.

The principles

Everything below follows from one idea: the report is a decision tool, not a testing diary.

PrincipleIn practice
Audience first Leadership wants the verdict and the risks in 30 seconds; developers want repro steps and evidence. Put the summary on top, details in appendices.
Facts, not adjectives “Checkout button returns HTTP 500 on submit” beats “checkout is broken”. Quantify: “fails 3/10 attempts”.
Reproducible Anyone with the build ID, environment, account role and steps can reproduce it — or you have written an anecdote, not a defect.
Scope-honest State what was not tested (features, browsers, edge cases, blocked areas). Residual risk is the most valuable section for a decision-maker.
Actionable Every failure carries a severity, an owner or suggested owner, and a next step: fix now, defer, or accept the risk.
Consistent Same template, same ID scheme (TC-123, BUG-456), same severity scale every time.

What a summary report contains

Order matters: the reader should reach the verdict before the detail.

  1. Metadata. Report ID, author, testing window, build identifier (git SHA or build number), environment URL, test data set, and the feature flags that were on.
  2. Executive summary. Pass, fail and blocked counts, requirement coverage, a verdict — Go / No-Go / Go with conditions — and the three to five things the reader must know.
  3. Scope. In scope, out of scope, and why (risk-based exclusions, blocked dependencies).
  4. Approach. Manual or automated, test types run (smoke, regression, cross-browser, accessibility, performance), tools and CI links. Link to raw results (Allure, Playwright HTML report, JUnit XML) instead of pasting logs.
  5. Results. Per feature or requirement, with the status breakdown below. Traceability to tickets and stories lets people judge coverage, not just pass rate.
  6. Defects. Open bugs sorted by severity, each row linking to its full ticket.
  7. Risks, known issues and deferred items. What is still broken, and why that is acceptable — or not.
  8. Recommendation. Explicit, with conditions: “ship if BUG-456 is fixed and the accessibility pass clears before GA”.

Three report types, kept separate

Defect report
Per bug, written as found, immediately.
Daily status
Short, during execution: progress, blockers, new defects.
Summary / sign-off
At exit, decision-oriented: verdict, coverage, risks.

Mixing the three is the most common reporting failure. A defect buried in a status update, or a verdict buried in a bug list, helps nobody.

Report statuses properly

Never collapse everything into pass or fail. Each status below is a different fact about the run.

StatusMeaning
PassedVerified against the expected result.
FailedVerified against the expected result; the result differed.
BlockedCould not run: a dependency is broken or the environment is down.
Not run / skippedOut of scope or deprioritized. Must be declared, never implied.
FlakyPassed and failed across runs; report the rate, not the last result.
The number to distrust

“100% passed” is meaningless if 40% of the suite was skipped. Pass rate without coverage is the most misleading metric in QA reporting.

Other metrics worth including: requirement coverage, open defects by severity, defect density per feature, escaped defects, flake rate, and total execution time. Leave out vanity metrics such as the raw number of test cases executed.

Details that make a web UI report credible

On the web, the environment is part of the result. The same build passes in one browser and fails in another, and a report without the environment cannot say which.

Environment matrix: always exact

  • Browser and version (never “latest Chrome”), operating system, device.
  • Viewport and resolution, zoom level, desktop or mobile.
  • Locale, timezone, and network throttling for performance or loading issues.
  • User role and permissions, feature-flag or A/B bucket, and the data set used.

Evidence beyond a screenshot

  • Annotated screenshot with an arrow on the failing element.
  • Short screen recording for dynamic issues (Playwright trace, Loom, QuickTime).
  • Browser console errors, verbatim.
  • Network tab or HAR file: status codes, payloads, CORS errors.
  • Whether it reproduces in incognito, or after clearing cache and cookies.
  • Reproduction rate, and whether the failure is intermittent.

Cover explicitly, or declare out of scope

  • Browsers: Chrome, Safari, Firefox, Edge; plus iOS Safari and Android Chrome.
  • Responsive breakpoints around each design target.
  • Accessibility to WCAG 2.2 AA: keyboard-only navigation, a screen reader (VoiceOver or NVDA), contrast, 200% zoom.
  • Localization: long strings and right-to-left layouts where relevant.
  • Performance budgets or Core Web Vitals, if in scope.
  • Session edge cases: expiry, the back button, refresh, deep links, multiple tabs, slow or offline networks.

Writing a defect: one per report

The defect entry is the highest-leverage text a QA engineer writes. This is the shape that survives review.

BUG-456 · defect report 
BUG-456 — Checkout returns HTTP 500 when the cart has a discount code
Severity: Critical (blocks purchase) | Priority: P1
Build: 3f2a91c | Env: staging, Chrome 142 / macOS 15 / 1440×900
Role: signed-in customer | Flags: checkout_v2=on

Preconditions: cart has ≥1 item; user holds a valid SAVE10 code
Steps:
  1. Add any item to the cart
  2. Go to /checkout, enter SAVE10, click Apply
  3. Click "Place order"
Expected: order confirmation page, order created
Actual: button spins, then toast "Something went wrong"; Network tab shows
        POST /api/orders → 500 (response body attached)

Evidence: recording.mp4, console-errors.txt, orders.har, screenshot.png
Repro rate: 10/10 | Also fails in incognito: yes | Safari: not tested
  • Minimal numbered steps: the shortest path to the failure.
  • Expected and actual, always both.
  • Separate severity (impact: blocker, critical, major, minor, trivial) from priority (urgency to fix).
  • No severity inflation. Credibility is a budget you spend once.
  • Never “it doesn’t work” without the exact symptom and reproduction rate.

What to leave out

Each of these costs the reader trust. Drop them before adding anything new.

  • “All tests passed” with no scope or build ID.
  • Screenshots with no steps or environment.
  • Several bugs crammed into one ticket.
  • Raw logs pasted instead of linked.
  • The ship / no-ship verdict buried on page nine.
  • Hedged language (“it seems like…”) where the observed fact and your confidence would do.
  • Reporting only the happy path, silently omitting blocked and skipped areas.
  • Editing the template after the fact instead of agreeing exit criteria before testing starts.

Copy, paste, adapt

Two starting points: the release summary below and the defect entry above. Keep the structure; localize the labels.

<2–4 sentences: coverage, worst open issues, the decision needed>

Passed X | Failed Y | Blocked Z | Not run W | Flaky V
Requirement coverage: N/M (linked list)

| ID | Severity | Title | Owner | Status |

…

## Evidence

The report worth optimizing for: a release manager skims the top ten lines, trusts the numbers because scope is stated, and can forward one bug link to a developer without asking you a single follow-up question.

Cách viết báo cáo kiểm thử QA

Báo cáo kiểm thử tồn tại để người khác ra quyết định — phát hành, sửa trước, hay dừng lại — với ít phải đọc nhất. Kiểm thử giao diện web thêm một quy tắc: môi trường là một phần của kết quả.

7 phần 2 biểu mẫu sao chép được 5 trạng thái kết quả
Tóm tắt kiểm thử · mẫu 3f2a91c
GO CÓ ĐIỀU KIỆN
  • Đạt 142
  • Không đạt 4
  • Bị chặn 2
  • Bỏ qua 6
Đã xác minh trên Chrome 142 · Safari 19 · Firefox 143

Các nguyên tắc

Mọi phần dưới đây xuất phát từ một ý: báo cáo là công cụ ra quyết định, không phải nhật ký kiểm thử.

Nguyên tắcThực tế áp dụng
Người đọc là trên hết Lãnh đạo muốn kết luận và rủi ro trong 30 giây; lập trình viên muốn bước tái hiện và bằng chứng. Tóm tắt đặt lên đầu, chi tiết xuống phụ lục.
Sự thật, không phải tính từ “Nút thanh toán trả về HTTP 500 khi gửi” tốt hơn “thanh toán bị lỗi”. Định lượng: “lỗi 3/10 lần thử”.
Có thể tái hiện Bất kỳ ai có mã build, môi trường, vai trò tài khoản và các bước đều tái hiện được — nếu không, đó là giai thoại, không phải báo cáo lỗi.
Trung thực về phạm vi Nêu rõ những gì không được kiểm thử (tính năng, trình duyệt, ca biên, phần bị chặn). Rủi ro tồn dư là phần giá trị nhất với người ra quyết định.
Có thể hành động Mỗi lỗi cần mức độ nghiêm trọng, người phụ trách (hoặc đề xuất), và bước tiếp theo: sửa ngay, hoãn, hay chấp nhận rủi ro.
Nhất quán Cùng một biểu mẫu, cùng quy ước ID (TC-123, BUG-456), cùng thang mức độ ở mọi lần.

Báo cáo tổng kết gồm những gì

Thứ tự quan trọng: người đọc phải thấy kết luận trước phần chi tiết.

  1. Siêu dữ liệu. Mã báo cáo, tác giả, khoảng thời gian kiểm thử, định danh build (git SHA hoặc số build), URL môi trường, bộ dữ liệu kiểm thử, và các cờ tính năng đang bật.
  2. Tóm tắt điều hành. Số lượng đạt, không đạt và bị chặn, độ phủ yêu cầu, một kết luận — Go / No-Go / Go có điều kiện — và ba đến năm điều người đọc bắt buộc phải biết.
  3. Phạm vi. Trong phạm vi, ngoài phạm vi và lý do (loại trừ theo rủi ro, phụ thuộc bị chặn).
  4. Cách tiếp cận. Thủ công hay tự động, các loại kiểm thử đã chạy (smoke, hồi quy, đa trình duyệt, khả năng tiếp cận, hiệu năng), công cụ và liên kết CI. Liên kết tới kết quả thô (Allure, Playwright HTML report, JUnit XML) thay vì dán log.
  5. Kết quả. Theo từng tính năng hoặc yêu cầu, kèm phân rã trạng thái bên dưới. Truy vết tới ticket và story để người đọc đánh giá độ phủ, không chỉ tỷ lệ đạt.
  6. Lỗi. Các lỗi còn mở sắp xếp theo mức độ, mỗi dòng liên kết tới ticket đầy đủ.
  7. Rủi ro, vấn đề đã biết và mục hoãn lại. Cái gì còn hỏng, và vì sao có thể chấp nhận — hoặc không.
  8. Khuyến nghị. Dứt khoát, kèm điều kiện: “phát hành nếu BUG-456 được sửa và đợt kiểm tra khả năng tiếp cận đạt trước GA”.

Ba loại báo cáo, đừng trộn lẫn

Báo cáo lỗi
Từng lỗi một, viết ngay khi phát hiện.
Trạng thái hằng ngày
Ngắn, trong lúc thực thi: tiến độ, tắc nghẽn, lỗi mới.
Tổng kết / ký duyệt
Khi kết thúc, hướng tới quyết định: kết luận, độ phủ, rủi ro.

Trộn lẫn ba loại này là lỗi báo cáo phổ biến nhất. Một lỗi bị chôn trong cập nhật tiến độ, hay một kết luận bị chôn trong danh sách bug, không giúp được ai.

Báo cáo trạng thái cho đúng

Đừng gộp tất cả thành đạt hoặc không đạt. Mỗi trạng thái dưới đây là một sự thật khác nhau về lần chạy.

Trạng tháiÝ nghĩa
ĐạtĐã xác minh, khớp với kết quả mong đợi.
Không đạtĐã xác minh nhưng kết quả khác mong đợi.
Bị chặnKhông thể thực thi: phụ thuộc bị hỏng hoặc môi trường sập.
Chưa chạy / bỏ quaNgoài phạm vi hoặc giảm ưu tiên. Phải khai báo rõ, không được ngầm hiểu.
Chập chờnĐạt và không đạt qua các lần chạy; báo cáo tỷ lệ, không phải kết quả lần cuối.
Con số đáng ngờ nhất

“Tỷ lệ đạt 100%” vô nghĩa nếu 40% bộ kiểm thử bị bỏ qua. Tỷ lệ đạt mà thiếu độ phủ là chỉ số gây nhầm lẫn nhất trong báo cáo QA.

Các chỉ số khác nên có: độ phủ yêu cầu, số lỗi mở theo mức độ, mật độ lỗi theo tính năng, lỗi lọt ra ngoài (escaped defects), tỷ lệ chập chờn, và tổng thời gian thực thi. Bỏ qua các chỉ số hình thức như số lượng test case đã chạy.

Những chi tiết làm báo cáo UI web đáng tin

Trên web, môi trường là một phần của kết quả. Cùng một build có thể đạt trên trình duyệt này và lỗi trên trình duyệt khác; báo cáo thiếu môi trường thì không thể nói là trường hợp nào.

Ma trận môi trường: luôn chính xác

  • Trình duyệt và phiên bản (không bao giờ “Chrome mới nhất”), hệ điều hành, thiết bị.
  • Viewport và độ phân giải, mức zoom, desktop hay mobile.
  • Locale, múi giờ, và điều kiện mạng (throttling) cho các vấn đề hiệu năng hoặc tải trang.
  • Vai trò và quyền người dùng, nhóm cờ tính năng hoặc A/B, và bộ dữ liệu đã dùng.

Bằng chứng ngoài ảnh chụp màn hình

  • Ảnh chụp có chú thích, mũi tên chỉ đúng phần tử lỗi.
  • Video ngắn cho các vấn đề động (Playwright trace, Loom, QuickTime).
  • Lỗi console trình duyệt, nguyên văn.
  • Tab Network hoặc tệp HAR: mã trạng thái, payload, lỗi CORS.
  • Có tái hiện trong incognito, hoặc sau khi xóa cache và cookie hay không.
  • Tỷ lệ tái hiện, và lỗi có chập chờn hay không.

Phải bao phủ rõ ràng, hoặc tuyên bố ngoài phạm vi

  • Trình duyệt: Chrome, Safari, Firefox, Edge; thêm iOS Safari và Android Chrome.
  • Các điểm ngắt responsive quanh từng mục tiêu thiết kế.
  • Khả năng tiếp cận theo WCAG 2.2 AA: điều hướng chỉ bằng bàn phím, trình đọc màn hình (VoiceOver hoặc NVDA), độ tương phản, zoom 200%.
  • Bản địa hóa: chuỗi dài và bố cục phải-sang-trái (RTL) khi áp dụng.
  • Ngân sách hiệu năng hoặc Core Web Vitals, nếu trong phạm vi.
  • Các ca biên của phiên: hết hạn, nút Back, refresh, deep link, nhiều tab, mạng chậm hoặc offline.

Viết báo cáo lỗi: mỗi báo cáo một lỗi

Mục báo cáo lỗi là đoạn văn có đòn bẩy cao nhất mà kỹ sư QA viết. Đây là dạng thức trụ được qua review.

BUG-456 · báo cáo lỗi 
BUG-456 — Thanh toán trả về HTTP 500 khi giỏ hàng có mã giảm giá
Mức độ: Nghiêm trọng (chặn mua hàng) | Ưu tiên: P1
Build: 3f2a91c | Môi trường: staging, Chrome 142 / macOS 15 / 1440×900
Vai trò: khách hàng đã đăng nhập | Cờ: checkout_v2=on

Điều kiện trước: giỏ hàng có ≥1 sản phẩm; người dùng có mã SAVE10 hợp lệ
Các bước:
  1. Thêm một sản phẩm bất kỳ vào giỏ
  2. Vào /checkout, nhập SAVE10, bấm Áp dụng
  3. Bấm "Đặt hàng"
Kỳ vọng: trang xác nhận đơn hàng, đơn hàng được tạo
Thực tế: nút quay vòng, sau đó hiện toast "Đã xảy ra lỗi"; tab Network cho thấy
        POST /api/orders → 500 (nội dung phản hồi đính kèm)

Bằng chứng: recording.mp4, console-errors.txt, orders.har, screenshot.png
Tỷ lệ tái hiện: 10/10 | Cũng lỗi trong incognito: có | Safari: chưa kiểm tra
  • Các bước ngắn nhất, đánh số: đường ngắn nhất tới lỗi.
  • Luôn có cả kỳ vọng và thực tế.
  • Tách mức độ (tác động: chặn, nghiêm trọng, lớn, nhỏ, không đáng kể) khỏi ưu tiên (độ khẩn cấp để sửa).
  • Không thổi phồng mức độ. Uy tín là ngân sách chỉ tiêu được một lần.
  • Không bao giờ viết “không hoạt động” mà thiếu triệu chứng chính xác và tỷ lệ tái hiện.

Những điều không nên viết

Mỗi điều dưới đây đều làm mất niềm tin của người đọc. Bỏ chúng trước khi thêm bất cứ thứ gì mới.

  • “Tất cả kiểm thử đều đạt” mà không có phạm vi hay mã build.
  • Ảnh chụp màn hình không kèm bước tái hiện và môi trường.
  • Nhiều lỗi nhét chung vào một ticket.
  • Dán log thô thay vì liên kết tới chúng.
  • Chôn kết luận phát hành ở trang thứ chín.
  • Ngôn ngữ rào đón (“có vẻ như…”) trong khi sự thật quan sát được và độ tin cậy của nó là đủ.
  • Chỉ báo cáo luồng thuận (happy path) và lặng lẽ bỏ qua phần bị chặn hoặc đã bỏ.
  • Sửa biểu mẫu sau khi kiểm thử xong thay vì thống nhất tiêu chí kết thúc từ trước.

Sao chép, dán, điều chỉnh

Hai điểm khởi đầu: báo cáo tổng kết phát hành (dưới đây) và báo cáo lỗi (ở trên). Giữ nguyên cấu trúc, bản địa hóa nhãn.
